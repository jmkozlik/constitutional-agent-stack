# F35 — the `callers_unknowable` iff has no category qualifier

**Status:** open, non-blocking. Filed report 011. Ratifier declined to rule;
revisit with the confidence-granularity work. **The contract stands as
blind-verified.**

## What it is

`Row.callers_unknowable` is specified as an unqualified *iff*: set when the
old index records unresolved sites in the symbol's importer set, where that
set is the symbol's own file plus every file importing its defining module.
The definition names no row category, so it applies to every row — `moved`
and `body` rows included, which have already established that callers are
unaffected.

## Why it was not ruled, and why that is right

The observation was raised *by* the implementation being faithful. Narrowing
the iff pre-emptively would have destroyed the measurement that makes the
question askable. The ratifier's position — contract stands, revisit with
confidence-granularity — preserves both the blind verification and the option.

## Candidates, none self-ratified

1. **Leave as written.** The flag means exactly what it says; a consumer that
   cares about caller-bearing categories filters by category itself. Costs
   nothing, and 51 of 53 rows carrying a flag that changes no decision is
   noise a downstream reader must learn to ignore.
2. **Scope the iff to caller-bearing categories** (`signature`, `deleted`,
   `unknown`). A spec change. Makes the flag actionable wherever it appears,
   at the cost of a row that *is* unknowable no longer saying so.
3. **Fold the own-file clause into `confidence`.** The executor's second
   observation: `confidence: low` already means "this file has an unresolved
   record", so the own-file half of the importer set is largely a restatement.
   Deduplicating them is the confidence-granularity work this was deferred to.

**Relevant fact for whichever is chosen:** the flag is not indiscriminate —
only 3 of 42 files in this repo carry unresolved sites. The 51/53 figure comes
from one commit touching one of those three, not from the rule being loose.

# F36 — the handoff channel breaks packet replay

**Status:** open. **BLOCKING for the replay guarantee**, gating nothing else
until ruled. Filed report 012. **This one is mine**, introduced in report 010.

## What it is

Replay's guarantee was that a shipped packet is reproducible from **(spec at
the pinned commit, join version at that commit)** — F23 closed on exactly
that, and on the corollary that a `DIVERGED` verdict indicts the packet rather
than the compiler.

Report 010 added `dispatch prepare --handoff`, which injects operator-authored
text into the packet's handoff section. That text lives in a scratch file. It
is in neither the spec nor the commit. **So any packet carrying a handoff is
no longer rebuildable from what replay reads**, and the corollary is false for
those packets.

## Evidence

The loop's own evals reader surfaced this on its first run — 2 DIVERGED, and
they are precisely the two dispatches I injected a handoff into (3d-1r, 3d-2).
Cause confirmed rather than assumed:

```
DIVERGED  node=index_assembly role=executor commit=f146eb16d654
--- shipped
+++ rebuilt
@@ -615,155 +615,5 @@
 
 ## State — handoff  [provenance: agent-authored, claim not fact]
 
-Carried forward from dispatch 3d-1 (same node's work, now owned by
-index_assembly after the ratified restructure). Provenance: the first
-section is the previous executor's own words; the second is the
-dispatcher answering the blocking REQUEST_MEM lines it stopped on.
-
```

The divergence is **entirely** the handoff section, empty on rebuild. Nothing
else in either packet differs.

## What I have already done about it, and what I have not

**Done — the citation rule, mechanised.** Per the ruling, no replay line is
cited as IDENTICAL until this is settled. Rather than rely on remembering
that, the evals tool now qualifies its own output:

```
replay: 4 packets on record — 2 DIVERGED, 2 IDENTICAL* (NOT CITABLE — F36 open)
F36 OPEN: replay verdicts above are marked NOT CITABLE. A packet carrying an
injected handoff is not rebuildable from the commit, so IDENTICAL does not
currently mean what reports have read it to mean.
```

A single `F36_OPEN = True` flips it off in the same commit that settles the
finding, and the qualifier disappears from every report that quotes the tool.

**Not done — the fix.** All three candidates change what a packet hash means,
which is a ratification, not plumbing.

## Candidates, none self-ratified

1. **Commit the handoff before building the packet** (e.g.
   `docs/evidence/stepN/handoff.md`), so it is part of the commit replay reads
   from. **Restores the original guarantee exactly** — packet reproducible
   from spec + commit + join version, no new inputs. Costs one commit per
   dispatch, and makes the handoff public before the dispatch runs.
   *My recommendation.*
2. **Record the handoff's sha256 in the dispatch record; replay takes
   `--handoff`.** Reproducible *given the recorded artifact* rather than from
   the commit alone. A weaker guarantee, but honestly labelled, and it keeps
   the handoff out of the repo's history.
3. **Exclude the handoff section from the comparison.** Cheapest and worst: it
   makes replay silent about the one section a human wrote, which is the
   section most likely to be wrong.

**Independent of the choice:** `dispatch harvest` does not currently copy the
handoff at all. The input to a dispatch is evidence and should be harvested
under any of the three.

## What this costs while open

Every past report that cited a replay line as IDENTICAL did so under the old
reading. Two packets on record (3d-1r, 3d-2) are affected; the other verdicts
predate the handoff channel and are unaffected in substance — but per the
ruling none of them is being re-cited here either.
