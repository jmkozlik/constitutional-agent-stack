## D-3d1-1 — BLOCKING — the spec's two `origins` lines contradict each other

**Filed against:** `harness/specs/analyzer.yaml`, the interaction of two
[authored] lines —

- `symbol_table.surface.types`: *"the index adds a top-level imports table —

consumer tests origins against a defining **module**. Those are different

literal `symbol_table` reading the equality the consumer performs can never

(b) shows the re-export chase already works for a **called** name — that

**What a fix would require.** A ruling on one line of spec, then the
implementation is small and lands wholly inside this node's write scope. The
three candidate rulings, with what each costs:

1. **Origins are symbol paths** (literal `symbol_table` reading). Cheapest to
   emit — it is the Resolver's output unmodified. Requires amending
   `affected_symbols` so the consumer derives a module from a symbol path

   helper` and `from pkg import Widget` become indistinguishable, both
   reporting origin `pkg.impl`.
3. **Both, in one list** (or one entry carrying two fields). Loses nothing
   and lets the consumer match on either, at the cost of a wider entry shape
   than the spec line currently writes — so the spec line changes either way.

My reading, offered as a claim and not acted on: (3) is what the two lines
*jointly* describe, and (2) is the minimum that makes the declared consumer's
own done_when bullet true. I did not pick. Picking would decide

## RULING NEEDED — D-3d1-1: what is an `origin`?

This is the one thing blocking 3d-1, and it is a defect in **D1-B as I
applied it this session** — both lines went in verbatim, and verbatim is how
the contradiction got in.

- `symbol_table` says origins are *"dotted origins as resolved by the
  reference layer, re-export chase included"* — the reference layer resolves
  to indexed **symbol** paths.
- `affected_symbols` tests *"any binding whose resolved origin is the
  symbol's defining **module**"*.

Different namespaces, and the index holds no module records at all — the
executor demonstrated it through the surface: `import pkg.impl`, imported
but never called, leaves **no trace anywhere in the returned index**, which
is precisely the edge the imports table exists to carry. The re-export chase
already works for *called* names; it is the uncalled module binding that
falls through.

The three candidate rulings, as filed (I am not picking):

1. **Origins are symbol paths.** Cheapest — the Resolver's output unmodified.
   Requires amending `affected_symbols` to derive a module from a symbol
   path, and still leaves bare `import pkg.impl` yielding nothing, so the
   *"module imports"* clause in its own line stays unsatisfied.
2. **Origins are module paths.** Satisfies the consumer directly and covers
   bare module imports. Costs resolution: `from pkg import helper` and
   `from pkg import Widget` become indistinguishable.
3. **Both, in one entry.** Loses nothing, lets the consumer match on either,
   and widens the entry shape — so the spec line changes under any ruling.

The executor's own reading, offered as a claim it did not act on: (3) is what
the two lines jointly describe, and (2) is the minimum that makes the
declared consumer's done_when true. Mine agrees, and I note the same caveat
it did — the entry shape changes whichever you pick, so this is a spec edit
either way.

**Struck from the blocker list, with measurement:** whether out-of-scope
consumers tolerate a new top-level `imports` key. They do — full suite 234
passed both without and with an injected key, with a control proving the
injection reached the test modules.
